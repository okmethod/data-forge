## 全体構成

パイプラインは **① 取得** → **② 合成** → **③ 出力** の 3 段が一方向に流れる。  
各段は共有の基盤層（出典メタ型・来歴語彙・設定）にのみ依存し、段同士は直接依存しない。

> 用語: 「段」はこのフロー上の処理ステップ（取得/合成/出力の3つ）、「層」は依存グラフ上の単位を指す。  
> 取得/合成/出力は段かつ層で、基盤層・参照層は段に属さない層。

- **入口・レジストリ** — 「何を・どの型で作るか」を宣言的に定義し、CLI がコマンドを dispatch する。データセット追加は原則この宣言を1つ足すだけで済ませる。
- **基盤層** — 出典 citation を運ぶ出力契約型・行の確からしさ（確定／速報）を表す来歴語彙・設定。段に属さず、各段が一方向に参照する。
- **参照層** — 段に属さない共有の参照データ層。全ファクトが共有する conformed dimension を置く（**星座型アーキテクチャ**のハブ）。現状の住人は合併畳込の材料となる**地域マスタ**のみで、**基準年集約**（合成とは別配線の集約ステップ）が地域正規化時に参照する（別軸の conformed dimension が要れば同じ層に加わる）。
- **① 取得＋クレンジング** — ソース固有。生データを取得し、年ごと・ソースごとの表差をこの段で吸収して共通の出力スキーマへ写像する。出典 citation もこの段（各ソース）が生成する。
- **② 合成（純変換）** — 基底データセットを時系列・広域へ合成する派生（**縫合／射影**）。
- **③ 出力** — 精製済み DataFrame を多形式へ書き出し、全成果物に出典メタを埋め込む。ソース非依存。

### 依存の向きの原則

取得層・出力層・合成層・参照層は互いに依存せず、共通の出典メタ型・共通の出力スキーマにのみ依存する。
特に縦結合（＝縫合）と基準年集約は相互に依存させず、オーケストレーション層が clean→縦結合→基準年集約 の順に配線する。

各層の独立は「異物の責務を層の外に出す」ことで保つ。  
集約（area 依存）は縦結合に埋め込まず基準年集約へ分離し（埋め込むと合成層が特定の参照層＝地域に縛られ本質軸がブレる）、citation 生成は出力層に置かず各ソースの責務とする（出力層はソース非依存で書き出すだけ）。

> **`area/` の非依存性の範囲（注意）:** 確実なのは**データセット非依存**（population 固有でない）まで。
> **ソース非依存ではない**——アトム抽出は各ソースの area 表現に依存する（今は e-Stat の area 階層前提）。
> 再利用できるのはコード軸が JIS（全国地方公共団体コード）で揃う範囲で、特に events（合併の後継）は JIS コードの事実なのでソースをまたいで使い回したい核。メッシュ/小地域/都市雇用圏など別コード体系の統計とは噛み合わない点に注意。
> 現状 consumer は population(e-Stat) の1例のみのため非依存は主張せず、e-Stat 前提で作り2例目で検証する。

## データ合成の 2 派生フロー（縫合 / 射影）

合成層は縫合（year 軸の結合）と射影（area 軸の union）の 2 変換を持ち、
ロード時に基底 / 縫合（`StitchedDataset`）/ 射影（`ProjectedDataset`）を判別して配線する。

- **縫合（stitch）**: 各回帳票（年ごと別 statsDataId）を year 軸で結合し合併畳込 等を通す既存フロー。
- **射影（project）**: e-Stat 既製の時系列帳票（1 ID が全年）を area 軸で union するだけの最小フロー（area master 不要）。

> 各型（`StitchedDataset` / `ProjectedDataset`）の汎用意味論（既定 join・grain・速報 splice の契約）はそれぞれの docstring がコード正典。
> 個別データセットの適用例は [docs/datasets/population.md](datasets/population.md) を参照。

## 星座型ハブ（地域マスタ）

年をまたぐと市町村合併・政令市移行で地域集合が変わる。  
実用グレードの連続時系列を成立させるには、地域を単一ファクトに閉じ込めず横断的に正規化する軸が要る。

そこで**地域マスタ**を、特定ファクトに属さない **conformed dimension（統一ディメンション）** として参照層に置く。  
地域マスタ自体はアトム（不可分の地域単位）を軸にした**スタースキーマ**だが、それを全ファクト（population / population_by_age / 将来の兄弟）が共有することで、複数のスターが1つの次元を囲む**星座型（fact constellation）アーキテクチャ**とした。

この地域マスタを消費するのが**基準年集約**で、指定した基準年（`base_year`）の地域区分へ、events（合併の後継関係）で他年次の地域を畳み込んで連続時系列に集約している。  
全体構成で示した層分離のとおり、合成（縫合）とは別配線で、参照層の地域マスタにのみ依存する。

設計・運用（アトム抽出・events・基準年集約 / crosswalk・人口保存検証・堀＝overrides）の正典は
[docs/datasets/area_master.md](datasets/area_master.md)。

## 拡張の接ぎ目（seam）

| やりたいこと                | 接ぎ目（足す宣言・概念）                                                                           |
| --------------------------- | -------------------------------------------------------------------------------------------------- |
| e-Stat の別データセット追加 | cleaner を1つ書き、レジストリに `Dataset` を1エントリ                                              |
| データセット固有パラメータ  | `Dataset.source_params`（ソース語彙をここに閉じ込める）                                            |
| 出典メタの項目追加          | 出典メタ型 `SourceMeta` に項目追加＋各ソースの抽出を更新                                           |
| 複数年を結合（縫合）        | レジストリに `StitchedDataset` を1エントリ（縫合変換を再利用）                                     |
| 既製の時系列を取込（射影）  | レジストリに `ProjectedDataset` を1エントリ（射影変換を再利用）                                    |
| 合併の後継対応を追加/修正   | events の overrides に1行足す（`area-orphans`/`area-check` で支援。コード変更不要）                |
| 地域正規化した時系列を出す  | 基準年集約に events・base_year を渡す（既存 union 等は生モードで併存）                             |
| 畳む/畳まないを固定せず出す | `--join crosswalk` で `base_code`/`base_name` 列を同梱（利用者が `GROUP BY base_code` で任意集約） |

## 抽象化の方針（実例2つで育てる）

原則は **「実例が2つ揃ってから抽象化する」**。対応する実作業とセットで導入し、逆依存など明確な欠陥だけ前倒し。  
以下は**順序ではなく**、各トリガーが起きたとき何を抽象化するかの対応（済/未は git 履歴が正典）。

| 抽象化のトリガー    | やる抽象化                                                                                                               |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 2つ目のデータセット | 地域コード正規化の共通層／年度パラメータ化／バリデーション規則                                                           |
| 2つ目のデータソース | `Source` プロトコル確定＋ CLI を registry dispatch へ。併せて生レスポンスを Pydantic で検証／設定は pydantic-settings 化 |
| D1 / R2 配信        | Exporter レジストリ化（フォーマットと transport の分離）                                                                 |
| データセット合成    | 派生2型（`StitchedDataset` 縫合 / `ProjectedDataset` 射影）＋ 合成層へ切り出す。汎用の依存グラフ化は3例目が出てから      |

> **2つ目のデータセット時の実地知見（cleaner の設計判断）:** 同名の帳票でも年（テーブル世代）で e-Stat のスキーマ設計が全く異なる（tab 軸の有無・男女軸の位置など）。
> そのため「入力パースの共通化」ではなく**年ごとの cleaner が共通の出力スキーマへ写像し、合成層で地域正規化する** 構成に落ち着いた。
> 具体的な年差の実例は [docs/datasets/population.md](datasets/population.md) の「年ごとのスキーマ差」を参照。
